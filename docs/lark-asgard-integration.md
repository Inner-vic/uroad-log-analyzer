# 飞书与阿斯加德接入边界

Uroad 标准链路不调用阿斯加德、不需要 lark-cli 用户派发 profile。它直接从车云获取 Uroad/CAN，生成 HTML，然后调用 `cc-connect-context.exe` 原生附件发送，等待与本任务来源绑定的同步回执。时延分析和走查的阿斯加德接入分别维护在其独立项目，不应把 fsdlog worker 复制进 Uroad。

## 部署必须准备

- 组织获准且支持原生附件同步确认的 CC Connect 可执行程序；本项目 delivery_bridge.py、task_worker.py、ccconnect_request_context.py 等调用与绑定代码均已包含。
- CC Connect 宿主的飞书 App/Bot 连接及已发布 IM/文件发送权限，正确加入来源会话；凭据由宿主受控存储管理。不能只安装 Python 源码就认为飞书已经可用。
- `UROAD_CC_CONNECT_BIN` 指向上述程序；多项目设置 `UROAD_CC_CONNECT_PROJECT` 为实际宿主项目，所有调度子进程继承同一配置。
- 入站传输首行原样保存，标准报告、附加问题与追问绑定原始任务/来源；原生回执必须确认任务产物路径、接收方和真实消息 ID。含用户名、token 的本机宿主配置不提交。

原生发送不可用或回执未知时保留原报告并标记未确认送达，不能改用 lark-cli 随意发到某个群来冒充成功。追问使用明确原线程或 job ID，不按最近报告匹配。

首次线上验收需明确获准请求，检查报告附件可打开、来源正确、实际消息回执以及 14 天保留数据追问。离线测试不证明宿主飞书授权可用。CC Connect 二进制是组织环境依赖，接手人应使用同一受验版本或经兼容验收的版本，不打包本机可执行程序和授权。
