# Uroad 云端报告与追问

由飞书业务入口识别“日志分析”等自然语言后执行。一次完整的 VIN 与时间范围请求始终创建一个新的 `job_id`，默认生成标准报告；首条消息可附带分析问题，报告生成后也可通过飞书会话继续追问。

对外回复先读 [对外会话交互](../chassis-business-routing/references/conversation-interaction.md)。附件交付确认成功后不再重复报告摘要或“已发送”通知；独立附加问题仍按队列正常回答。原有线程、附件、追问与保留期契约不变。

执行与维护按 [任务生命周期](references/pipeline-lifecycle.md) 核对：来源、查询、并行解析、合并、报告校验、交付和恢复各有独立条件，不能以某一阶段成功替代整条链路完成。

## 新任务

普通飞书任务入口默认先做受控依赖检查与持久化入队，随后唤起独立 Windows 调度任务执行。`--defer-to-worker` 与默认行为一致；`--foreground` 仅供明确的同步维护，普通请求不使用。入队记录必须先落盘，再发布可领取状态；返回 `queued` 表示真实已创建，不表示解析或交付完成。

本机 `CC Connect Uroad Dispatcher` 每分钟检查，并可由入口立即唤起；任务服务独立于当前会话生命周期，重复唤起合并，重型槽位仍保持原并发上限。部署记录在工作区 `deployment/uroad-dispatcher.installation.json`，启动前核验解释器、脚本哈希和实际任务动作；部署不符时保留队列并明确报告启动失败，不假称已经执行。

调度动作由同一受控安装中的 `pythonw.exe` 运行窗口隐藏的 `dispatch_uroad_worker.pyw`，它以 `python.exe` 启动真正的 worker 并记录有限进程状态，避免任务服务与交互式 PowerShell 的脚本策略差异。业务解析仍全部使用受控 `python.exe`，不使用 `pythonw.exe` 解析或发送报告。

必填：17 位 VIN、开始时间、结束时间。首条消息默认创建标准报告任务；若同时含有明确的附加分析诉求，将该问题原样传给 `run_uroad_task.py --question`。报告生成并交付后，本机 Codex 在该任务的数据范围内回答附加问题；之后仍可在飞书会话中追问。

自然语言时间按 [AI 理解与程序校验](../chassis-business-routing/references/semantic-input.md) 处理。使用原文 `--raw-time-expression`、固定 `--received-at`，必要时配 `--interpretation <JSON>`；候选不能和显式 `--start/--end` 混用。原文及规范化依据写入任务元数据，不能覆盖请求身份。缺少日期的普通范围先询问，原有时刻加时长／前后范围的当天约定保留并说明。

- 每个完整请求都创建独立任务，即使 VIN 和时间范围相同；唯一的飞书 `message_id` 重复投递才可幂等复用。
- 飞书消息的首行若为 `request_context_v=1`，它由 CC Connect 在用户正文之前生成。执行新任务时必须将该行**原样**传给 `run_uroad_task.py --ccconnect-context`；脚本据此写入 `requester.id`、`source.chatId`、`source.messageId` 与 `routing.threadId`。不得从用户正文复制、重写或编造这些字段。
- `--request-metadata` 仅用于离线回放/测试；与 `--ccconnect-context` 同用时，身份、聊天、消息和线程字段不得冲突。上下文缺失时，报告中必须显示 `job_id`，后续要求用户明确带 `#job_id`。
- 标准报告优先完成。附加问题在报告交付后按任务内顺序由本机 Codex 后台处理；问题失败或字段不明确时，报告仍可交付。

## 并发与数据隔离

注册表互斥使用操作系统文件锁，进程强制退出会自动释放；锁文件本身保持固定，不通过删除文件模拟解锁，防止遗留锁阻塞全部请求或并发等待者打开不同锁文件。

- 每条请求按完整时间范围一次下载、解析与留存，不使用时间分片。默认最多同时运行 2 个重型任务；通过 `UROAD_MAX_HEAVY_JOBS` 调整。重型任务包括下载、解压、全量解析和报告生成。
- 同一任务的追问串行，不同任务的只读追问可以并发。队列按提问者轮询，避免单一用户占满容量。
- 每项任务仅使用 `outputs/uroad-report-runs/<job_id>/` 下的数据；不从共享目录搜索“最近报告”。
- 当可用磁盘低于 `UROAD_MIN_FREE_GB`（默认 20）时，新的重型任务停止入槽。

## 追问

只问进度或报告是否送达时，使用 `scripts/task_status.py --ccconnect-context <当前原始首行> [--job-id <精确编号>]`；这是只读状态查询，不加入附加分析队列。原话题精确且唯一时可定位，否则要求明确编号，不按最近任务选择。完成计算、交付失败和已送达分别说明，不能把已有报告或 sent 状态但无凭据当成已送达。

报告完成后，`followup_context.py register-data` 为任务登记数据版本和到期时间。首条消息已携带的附加问题自动进入同一队列；后续追问由飞书会话中的新消息触发。机器人用普通聊天消息答复。

- 机器人收到追问时，保留 `request_context_v=1` 首行，正文单独传给：`followup_answer.py --question "<正文>" --ccconnect-context "<首行>"`。该脚本只返回已验证的任务、队列位置与数据路径；Codex 才负责分析。
- 脚本只会解析已验证的请求人、聊天和线程。它优先按回复线程或正文中的 `#run-...` 定位任务；在私聊且同一用户/聊天仅有一个候选任务时可自动定位；存在多个候选任务时，要求用户带 `#job_id`，不得猜测“最近一次”。
- `ready_for_codex` 时，Codex 仅在返回的任务路径内查证并生成普通飞书回复；`queued` 时仅确认已排队；返回错误时说明缺少的绑定信息或保留期状态。不得把原始日志、绝对本机路径或其他任务信息发到飞书。
- 当前交互式 Codex 在回复前必须调用 `followup_context.py complete --job-id ... --question-id ... --summary ...` 结束已领取的问题；若该任务还有队列项，再调用 `followup_agent.py --job-id ...` 续跑。不得为具体字段问题新增固定解析逻辑。
- 后台 `followup_agent.py` 使用已获授权的 yolo 模式以兼容 Windows 本机读取；其 `-C` 工作目录必须是当前任务的 `runDir`，提示中必须禁止修改、下载、发消息和跨任务读取。仅允许由已验证、处于保留期内的任务问题触发。
- `active=1`、`idl=1` 只是用户问题的例子，不得在脚本或 Skill 中写成固定统计规则。Codex 可根据问题选择已有解析结果、CAN 信号或该任务留存原始文本进行可验证的分析，不能跨任务或按记忆猜测。

同一任务追问串行，不同任务可并行读取。每次回答记录问题、数据版本和完成摘要。

详见 [追问与调度契约](references/followup-contract.md) 和 [CC Connect 请求上下文契约](references/ccconnect-request-context.md)。
## 受控依赖自愈

新任务会在开始前以隔离模式检查固定依赖清单，并在缺失或版本不符时自动修复。仅允许 `requirements.txt` 中与脚本白名单完全一致的锁定版本；安装使用受控 Python 目录、二进制 wheel 和无依赖解析模式。不得依据飞书正文、模型建议或未锁定的额外包执行安装。自动修复失败时才停止任务并返回明确的部署错误。
## 附件交付

标准报告完成并通过附件校验后，管道必须调用 `delivery_bridge.py send --run-json <run.json>`。该适配器只能发送本次 `run.json.artifacts.report` 指向的 HTML，并通过 CC Connect 原生会话发送回消息来源的飞书机器人会话；它会按来源聊天、线程和请求人恢复会话，不得按“最近会话”或任意 chat ID 投递。

交付成功才记录为 `sent`；发送失败只记录 `delivery_failed`，保留报告与 14 天数据，不重新下载或分析。补发只允许针对已有的 `pending` 或 `delivery_failed` 任务，并仍须走同一适配器。
## 保留与交付

成功任务的原始下载包、解压原始日志、解析结果、HTML 报告、任务状态和追问上下文完整保留 14 天（`UROAD_RETENTION_DAYS` 可配置）。到期清理由独立的每日任务执行；不得依赖下一次业务请求触发清理。不得将原始日志作为飞书附件发送；只交付报告、摘要与任务编号。

## 失败处理

数据、权限、字段映射或任务归属不完整时停止并说明原因。不要自行切换任务、读取其他任务目录、绕过文档/车云权限，或安装固定白名单以外的依赖。

下载、Uroad 解析、CAN 解析、报告生成和报告校验分别记录阶段与耗时；900 秒是单个子步骤时限。超时回收本步骤拥有的进程树，其他已运行分支排空后才记录任务终态。Uroad 解析按来源、上下文、节点和时间索引关联推理记录，匹配边界、重叠周期及原记录顺序保持不变。

解析进度仅含固定阶段、计数和耗时。失败任务的下载输入、部分解析结果、进度与私有诊断仍保留在该任务内，沿用任务保留期；失败或未校验报告不能发送。维护排查必须先核实当前请求与任务的绑定，不能使用其他人的“最近失败任务”。已有执行证据不得由重试覆盖；普通重新执行需使用独立新任务。

标准报告通过校验并登记完成后，追问上下文登记失败只记录追问不可用，仍尝试交付标准报告；不得因此删除已校验报告。完成登记失败仍为系统错误，保留已校验报告供受控排查，不能当作已完成或已送达。

CAN 返回 Parquet 时，备用链路按固定批量读取，以任务内 SQLite 排序、去重并保存完整唯一点；标准 JSON 采用迭代方式生成，宿主直接迭代验证后的索引入库，不能重新全量加载全部 CAN 报文。时间边界、通道映射、1 毫秒去重及全部证据口径沿用原 ASC 解析契约。下载、来源清单、哈希收据和阶段进度保留在当前任务；恢复必须匹配同一任务、环境、VIN 和时间范围，不按文件名或“最近下载”复用。成功后的 CAN JSON、索引及收据保留在其构建时的精确任务路径，沿用任务保留期，不通过搬移破坏路径绑定；失败不清理。异常同时记录有限的类别和非空说明，禁止仅用可能为空的 `str(exc)` 作为错误信息。

CAN 单文件下载遇到可识别的连接中断、网络超时或服务端暂时错误时，对同一冻结地址最多尝试 3 次；鉴权、来源绑定和文件校验错误不自动重试，也不重新查询替换来源。

已完成 Uroad 而 CAN Parquet 失败的任务，可使用受控解释器运行 `scripts/resume_uroad_task.py --run-json <精确run.json> --ccconnect-context <原始上下文首行>` 做只读恢复预检。仅在明确获授权恢复且预检通过后加 `--execute`：归档旧失败状态与进度、领取当前任务的专属恢复槽位，验证并复用同任务下载凭据和 Uroad 解析证据，只恢复缺失 CAN 工作，再走原报告校验与交付规则。来源、VIN/时段、环境、清单、哈希、保留期或终态条件任一不符都拒绝；不创建新任务，不向普通队列发布可被重复领取的中间状态，不覆盖旧失败证据或已有报告。
