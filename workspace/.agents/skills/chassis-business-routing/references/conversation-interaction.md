# 对外会话交互

用于走查测试、原时延分析和 Uroad 的接收、进度与结果回复。只调整沟通，不改变业务触发词、数据口径、身份、权限或任务绑定。

## 一次任务只交付一次结果

- CC Connect 已启用即时回执时，由它统一确认收到；业务脚本和助手不要再各发一次“已收到／已提交”。即时回执仅表示收到消息，不代表预检、派发或分析成功。
- 工具调用前的 commentary 在当前 quiet 配置中可能被隐藏，不能当作已向用户送达的消息。不要为补偿隐藏的 commentary 重复发送接收通知。
- 任务长时间执行时，按实际阶段简短更新，例如“正在获取两段日志”“两段数据已解析，正在生成报告”。没有状态变化时只说明仍在处理，不重复 VIN、完整时间窗、内部阶段码或文件计数。不要把每次 wait 的返回值逐条转发，也不承诺未经测量的完成时间。
- 原走查的独立执行服务负责节流发送阶段进度；精确任务记录已确认 `progress_sent` 时，助手继续跟踪但不重复播报同一阶段。无阶段变化时不增加通知，最终送达前停止进度发送。
- 成功报告由本业务原交付入口发送一次。当前轮确认本任务已成功投递后，不再追加“报告已完成”“已发送”或第二个报告链接，也不再发完成类 commentary。最终回复只包含 CC Connect 静默协议标记 `NO_REPLY`，独占一行且不带其他正文；它不会显示给用户。
- 静默必须有本任务、同一来源的投递凭据：发送 API 明确成功及相应交付状态。走查使用成功发送后写入的 `report_reply_mode=source_message_in_chat`／回复 message ID；Uroad 使用交付适配器的 `sent` 或已验证的 `already_sent`；原时延入口使用本轮 Bot 发送成功或明确的交付记录。仅有报告 URL、`queued`、`metrics_ready` 或含义不明确的旧 `completed` 不算送达。
- `正文 + NO_REPLY` 不会隐藏正文，不可用来去重。不要为制造凭据重发历史报告；状态不明时先核对本任务，不猜测、不自动重复投递。
- 用户另发新消息明确索要报告链接、摘要或解释时，应正常答复该问题；不因历史任务已交付而静默。
- 静默去重只针对标准报告的重复通知，不吞掉 Uroad 的独立附加问题或追问答案。交付轮若结束为静默，附加问题仍须已交由该任务队列继续处理。
- 走查仍在排队或执行时继续跟踪精确记录，不能用 `NO_REPLY` 提前结束等待。原时延和 Uroad 的后台入口可以在确认真实创建后结束接收轮：仅用一句说明实际状态及后续交付位置，不再复述收到回执；例如“任务已排队，报告完成后会发回本线程。”上游发送仍须有真实消息 ID，后台接收轮结束不表示任务完成。

## 按场景说清楚当前状态

| 场景 | 应说明的内容 |
| --- | --- |
| 缺少输入 | 一次列出真正缺失的字段，例如“还缺少第二段时间，请补充开始和结束时间。”不称已创建或已提交。 |
| 走查测试 | 只有需要补充说明时提示第一段 Base、第二段 PCM更新；正在取数、分析、发布分别按真实状态表达。成功由报告通知收尾，普通回复原消息，不新建话题。 |
| 原时延分析 | 上游消息 ID 落盘后才称已发送；等待阶段可说“正在等待两段结果，收到后生成对比报告”。保持原话题策略。 |
| Uroad 日志分析 | 区分排队、日志分析、报告交付。标准报告先交付；附加问题另行回答，内容与报告不同才有第二次结果消息。保持原线程与任务编号契约。 |
| 普通咨询／追问 | 直接回答问题，不套用“任务已受理／已生成报告”。已绑定的追问只查该任务数据，不按最近任务猜测。 |

“到哪一步了”“发出去了吗”等纯状态询问只读取原任务状态，不创建业务任务、不启动附加分析队列、不刷新云端授权。Uroad 使用原话题唯一绑定或显式任务编号的只读状态入口；原时延使用精确记录和当前请求上下文查询。无法唯一绑定时只补充任务编号或原话题位置，不按最新记录猜测。

Uroad 追问返回 `queued` 时，一句“你的问题已排队，将基于原报告继续分析”是队列状态说明，不是新任务接收回执；不再追加“已收到”。示例是表达参考，不是每个任务都要发送的固定消息清单。接收回执、进度和终态各有唯一发送者；不要为凑流程增加消息。

走查中“字段已识别但场景无有效值”只在表格显示 `-`，不额外解释；“字段未解析或识别证据不足”必须在同一条报告通知列出对应侧、场景与指标。此提醒是必要结果内容，不是重复完成通知；不另发第二条告警，也不能为了静默去重把提醒省略。

## 失败只说明事实和下一步

- 任务终态失败、交付失败或执行已结束却无法确认送达时，不能用静默掩盖：由当前会话普通回复一次脱敏原因和可执行的下一步，后台未发失败消息时由助手负责。这不要求在仍执行的后台任务上提前发送失败结论。
- 区分“未查到日志”“接口查询失败”“解析失败”和“分析完成但交付失败”。不能把权限或网络错误说成没有数据，也不能把已有 URL 说成已交付。
- 仅在本任务确实已有有效缓存时说明“结果已保留，恢复交付无需重新计算”。需要授权或管理员处理时明确缺少什么；不重复问空泛的“要不要继续”。新增授权仍须由有权人决定，不能绕过权限。
- 对普通用户使用中文业务语言；不展示 `ok/partial/queued`、模型、effort、token、ctx、工具命令、本机绝对路径、原始上下文头或内部堆栈。缺失指标如实保留，不包装成完整成功。

## 展示与验证

运行配置使用 `display.reply_footer=false`、`display.show_context_indicator=false`、`display.hide_agent_footer=true`，本项目 `show_workdir_indicator=false`。`hide_agent_footer` 不能替代 CC Connect 自身的页脚总开关。保留 quiet 模式及关闭 thinking/tool 消息，不把内部推理当作进度。

上线验证至少覆盖：输入不足只追问、同源重试不重复报告、成功一条结果、交付失败一条说明、普通聊天无模型用量及目录尾注。不要为了验证创建真实重型任务或向无关会话发送消息。
