# 上游接入约定与待确认事项

当前已完成的是独立结果消费模块：飞书在线表格 → 只读单元格 → 四场景 P99 JSON，
以及两个结果时段的 P99 对比。OpenClaw 触发层已能由上游卡片链接发起单次读取。
业务入口只读在线表格，不导出或下载 Excel，已移除文件输入及下载入口。
卡片检查只解析用户提供的 JSON，不读取飞书会话，不向另一个机器人发消息。
下一步优先复用上游结果服务；是否合入 uroad 主功能仍待决定。

## 需要上游提供什么

云端联调材料：“查看结果”打开后的实际飞书表格链接，以及有权读取该表格的机器人/用户身份。
真实链接和授权材料仅留在公司云电脑，本地开发无需提供。授权路径见 [云电脑部署与授权](openclaw-deployment.md)。
无需下载 Excel。卡片 JSON 可用于确认按钮指向的入口。
若不方便分享签名链接，提供脱敏后的地址结构、鉴权说明和返回类型即可。

1. **已有结果怎么拿**：用户已确认是飞书文档形式，需确认最终是 `/sheets/` 在线表格、
   `/wiki/` 下的表格，还是 Docx 中嵌入的电子表格；按钮是否先经过结果页/action 回调？
   表格是否每次新建、生成何时完成、有效期、所需身份及可供机器人使用的权限是什么？
2. **如何发起任务**：是否有可复用的 API/SDK？请求参数、任务 ID、状态查询或完成回调、
   失败状态与重复请求策略是什么？优先由现有分析服务提供接口，避免复制其日志下载/分析逻辑。
3. **结果如何对应请求**：提供版本/构建号、VIN、时区与起止时间、任务 ID、结果文件标识。
   当前 `metadata` 接受这些字段，但不会校验其业务含义或从 Excel 自动推断。
4. **表格契约**：确认 sheet 名、header 指标名、场景列表、P99 格式、缺值方式，以及是否会
   在同一 sheet 放多个平台或多段测试结果。多块同名指标当前返回歧义，后续应增加明确选择条件。

截图能证明人工可以从卡片查看结果，不能证明另一个机器人能够收到或执行 bot 发出的命令，
也不能证明机器人具有在线文档读取权限。不要把截图中的 `fsdlog` 示例自动发送出去。

## 确认后接在哪一层

主入口为 `scripts/ad_p99.py --sheet-url <链接>`，在线读取适配器在 `scripts/lark_source.py`。
适配器调用已配置的 `lark-cli`：`+revision-get`、`+workbook-info`、`+sheet-info --include merges`、
`+csv-get`（CSV 通过 stdout 进入内存，不写 CSV 文件），以 service 返回的行列坐标定位。
合并区域和单元格只形成内存网格，共用 `parse_loaded_book` 的场景匹配逻辑。
API 响应形状按本机已安装的 CLI 帮助和官方 skill 参考实现，实际公司表格仍待联调。

未来现有机器人只需返回在线表格 URL，再调用此入口；不必另起 Excel 导出流程。
若改用飞书 SDK，新的只读适配器也应提供同样的单元格值、真实坐标、合并区域和版本信息。
`parse_workbook(data, source_name=..., metadata=...)` 仅保留用于合成工作簿测试，不作为企业文档接入途径。
上游地址、凭据和任务参数属于后续适配器配置，不应硬编码到解析器或提交到交付目录。

针对在线表格应走当前只读单元格接口；SSO 网页或 action 回调需确认背后的表格地址和授权，
不能仅改链接后缀为 `.xlsx`。
如果公司禁止通过 API 获取这些单元格，不以 API 或浏览器复制来绕过限制；
由上游在公司批准的服务内解析并通过获准接口仅提供四个 P99，是待对接的替代方案。

## 刷包前后对比接入

一次“查看结果”卡片只能代表一个上游分析任务，不能自动推出另一个时段。
触发层应先从用户复制的自然语言中建立一条对比请求，保存以下最小上下文：`vin`、Baseline 起止时间、
替换后起止时间，以及两侧任务 ID。可复用 `parse_comparison_request(text)`：它支持每段都写 VIN，
也支持只写一个 VIN 后给两个时段；按时段先后分配角色，较新的时段必定是替换后。出现不一致 VIN、
时间段重叠、倒序或不恰好两个时段时停止并提示用户修正。两张完成卡片各自解析出在线表格链接后，调用
`ad_p99.py --baseline-sheet-url ... --replacement-sheet-url ...` 完成读取和差值计算。

不要以卡片到达先后决定 Baseline；以创建对比请求时绑定的任务 ID/时段角色为准。
同一任务的重复事件应按 message ID 或任务 ID 去重。只将完整四项的对比标为 `ok`；
任一侧缺场景时保留可用行并标为 `partial`。对比回复由 `table.columns`、`table.rows` 渲染，
差值固定计算为 **替换后 − Baseline**，单位 ms。

### 当前默认：手动 URL 交付

用户手动点击阿斯加德卡片的“查看结果”，复制最终 Sheets URL。URL 不需要 `?sheet=<id>`，读取器会
按工作簿中 `VLA`、`VLA Parking` 名称定位结果页。最快方式是“AD P99 对比 + 两个 URL”，此时按 URL
顺序计算 URL 2 − URL 1，并标记 VIN/时段由用户确认。需要系统校验同一 VIN/时段时，再将 VIN、两个
时段和两个带角色的 URL 发给 AD P99 机器人。这比转发卡片更稳定，也不依赖跨机器人事件。两个 URL
均到齐后立即调用 `ingest_manual_url_message` → `run_job` 完成分析。

若用户先提供一个 URL，必须同时给出 VIN、两个时段与 `Baseline` 或 `替换后` 标签；Skill 保存待补充
任务并返回 `comparison_key`。第二条消息使用 `角色 #comparison_key URL` 补全。没有两个时段或角色标签时，
不以 URL 粘贴顺序推断 Baseline/替换后。

### 已收敛的当前方案

阿斯加德已明确：它在用户与其直接会话的上下文中工作，不接受其他机器人的群聊 @ 消息，
也不能监听或接收机器人消息。因此不实现机器人到阿斯加德的自动调用。

1. 用户给 AD P99 机器人复制 VIN 与两个时间段；`half_auto.py create` 校验 VIN 和时间顺序，
   创建 `comparison_key` 并输出两条阿斯加德原始指令。
2. 用户在与阿斯加德的直接会话中先单独发送 Baseline 指令并等待其结果卡片，再以另一条独立聊天
   消息发送替换后指令。阿斯加德一次只解析一条 `fsdlog`，同一消息中的第二条会被忽略。
3. 用户将两张结果卡片分别回复并 @ AD P99 机器人。处理器读取当前卡片显示的起止时间，在状态目录
   中自动匹配角色；两张卡片可任意顺序到达。若转发不保留时间或一个时间段匹配多个任务，再以
   `Baseline #<comparison_key>`、`替换后 #<comparison_key>` 标记回复。转发不保留按钮时，回复带
   相同标记的最终 Sheets 链接。
4. 触发层调用 `attach_result`，两个角色均齐全后调用 `run_job`，生成 P99 对比表。

角色优先由卡片显示时间和已排序的时段绑定，不由卡片先后决定；时间缺失或匹配歧义时才使用用户标记。
一个角色只能接收一张卡片；重复提交会被拒绝，防止覆盖已经绑定的结果。每次卡片回复是独立的即时事件：
处理器只解析本条卡片和状态目录，不依赖主动翻阅聊天记录。

OpenClaw Feishu 通道负责接收用户 @、传入当前卡片 JSON 并发送回复；Skill 代码不自行订阅飞书事件
或发消息。部署适配器收到卡片事件后应调用 `ingest_card_event`：第一张返回等待状态，第二张自动完成
在线读取和对比。这个边界避免 Skill 私自读取聊天记录或模拟“查看结果”按钮点击。

### 两个上游任务的编排契约

对比请求应形成一条 `comparison_key` 记录，并以同一 VIN 的两个时间段创建两条独立上游任务：

```text
用户自然语言 → 规范化 comparison_key / VIN / 两个时段
             → 提交 Asgard（Baseline）→ upstream_task_id_a
             → 提交 Asgard（替换后） → upstream_task_id_b
             → 按 task ID 取得各自 result_sheet_url
             → 双表只读提取 → P99 对比表
```

需要一个由 Asgard 提供或由公司批准的适配器实现以下最小能力：

```text
submit(vin, start, end, context) -> { upstream_task_id }
get_result(upstream_task_id) -> {
  status: pending | completed | failed,
  result_sheet_url?: https://.../sheets/...
}
```

两个 `upstream_task_id` 必须和 `comparison_key` 的角色绑定；卡片到达顺序不参与配对。
上游完成后，适配器只交给 AD P99 Skill 该任务的表格 URL 与必要的任务元数据。

飞书群聊中的“查看结果”按钮可能只是 Asgard 应用自己的 callback 或跳转动作。该 callback 不会
自动转发给另一个应用机器人，且阿斯加德已确认不接受 bot-to-bot 调用，因此不以自动点击、群聊
@ 或定时轮询作为当前方案。若未来上游开放服务接口，升级优先顺序为：

1. Asgard 已提供的 API、MCP/Skill 或任务查询接口；
2. Asgard 团队增加 task ID 到 result_sheet_url 的只读查询接口或完成回调；
3. 经确认可用的飞书群消息桥接，用 task ID 关联卡片。

## 后续报告接口

四个场景以稳定名称 `slow_driver`、`fast_driver`、`CNOA`、`parking` 输出，单位固定 ms。
后续历史表扩展、横向追加列或发版报告填充应作为另一个消费者，使用 `status=ok` 的记录，
结合表格 URL、revision、任务/版本标识去重；本阶段不决定报告格式与历史数据存储方式。

## 已知范围

- 已实现：飞书在线表格只读适配器、版本一致性复核、分段读取和截断重读；
  合并指标块、缺失/歧义检测、坐标追溯、摘要输出及环境/文档清单预检。
- 范围之外：文档下载/导出、图片 OCR 作为实测数据、执行公式、上游任务调度和报告写入。
- 限制：每个目标 sheet 扫描范围 500000 格；当前读取两个目标 sheet 的单元格，不读取其余 sheet，
  仅输出四场景摘要。后续得到真实布局后可进一步缩小读取区域。

当前 47 项测试使用用户截图构造的工作簿和模拟 CLI 响应；本地环境预检通过但未接触文档。
真实权限、API 返回结构、云端 Linux 运行和四场景数据准确性，均需在公司 OpenClaw 云电脑验证。
